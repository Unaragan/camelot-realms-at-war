## What has changed in UE5.7/5.8 compared to previous UE5 versions (relevant to us)?

**Sources:** [Epic: UE5.8 Release Notes](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-8-release-notes), [Epic: UE5.7 Release Notes](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5-7-release-notes), [80.lv: UE5.8 Optimization Improvements](https://80.lv/articles/unreal-engine-5-8-is-out-today-with-big-optimization-improvements-and-mesh-terrain), [Tom Looman: UE5.7 Performance Highlights](https://tomlooman.com/unreal-engine-5-7-performance-highlights/), [StraySpark: UE5.8 Preview for Indies](https://www.strayspark.studio/blog/unreal-engine-5-8-preview-indie-features-2026), [Epic: Third Person Template Doku (5.8)](https://dev.epicgames.com/documentation/unreal-engine/third-person-template-in-unreal-engine?lang=en-US), [Epic: Motion Matching in UE (5.8)](https://dev.epicgames.com/documentation/unreal-engine/motion-matching-in-unreal-engine?lang=en-US)

- **UE5.8 Overall focus:** Not a "new rendering feature" release, but more reliable, scalable, and intuitive," according to Epic, which is good news for a performance goal project like ours (mid-range hardware, not lumen/nanite for characters) — less risk of new default rendering features undermining our conscious low-end choices.
- **Enhanced Input + Common Input/UI unified in 5.8:** According to the research, enhanced input and common input/UI workflows were merged — fewer duplicate input data assets, more reliable event handling, better widget binding. **Relevant to us:** If we are building hotbar keybinds/controller support, it is worth taking a look at whether the new unified system requires less manual IMC/IA juggling than the older enhanced input workflow that older GAS tutorials (2022–2024) still show.
- **Motion matching is officially documented in 5.8** (no longer just experimental sample) and the third-person template itself now uses the new IK rig system for its animation blueprints. **Attention:** That's a distinct difference from older GAS tutorials (2022–2023, mostly third person template with classic AnimBP + Blend Spaces à la Mannequin era). If the tutorial and current template setup don't fit together, it can look like a GAS bug, but it's an animation system version difference — the kind of trap that's cost us a lot of time at Lyra before. **Recommendation:** before deeper GAS expansion, check whether our current `CamelotRAW_TP`Project Motion Matching or classic AnimBP (variant "None" when creating probably still chooses the classic system, but this should be explicitly verified once).
- **ChaosMover/Mover system** Gets trajectory prediction for motion matching workflows, deeper chaos visual debugger integration, support for gameplay tags, and instant movement effects in 5.8 — moves further out of the experimental state, but is not yet finally stable, according to Release Notes. **For us:** Do not touch now, standard characterMovementComponent is sufficient for the Vertical Slice; keep in mind as a later option for dodge/sprint capabilities.
- **According to research, GAS itself has no major API breaks in 5.7/5.8** — the core classes ()`UAbilitySystemComponent`, `UGameplayAbility`, `UAttributeSet`, `FGameplayEffectSpec`) have been stable for several years. No reference in the release notes to Breaking Changes specifically for GAS. This is in line with the general experience that GAS tutorials are still largely 1:1 applicable even several years old (unlike the animation system, see above).
- No reliable public reference to replication/network breaking changes in 5.7/5.8 that affect our list server prototype setup. (Iris replication system still exists as an opt-in, not necessary for our scope — see README "Scaling")

## Known pitfalls in the manual GAS retrofit (third person template + own attribute set)

**Sources:** [Laura: Simple GAS tutorial](https://landelare.github.io/2024/01/15/simple-gas-tutorial.html), [Epic Forums: Gameplay Abilities & Attributes Set Replication](https://forums.unrealengine.com/t/gameplay-abilities-attribute-set-replication/134514), [GAS Companion Docs: Setting up ASC on Player State](https://gascompanion.github.io/asc-on-player-state/), [GAS Companion Docs: Quick Start](https://gascompanion.github.io/quick-start/), [Epic: Understanding the GAS (5.7 documentary)](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system), [Medium: GAS + Enhanced Input Binding](https://ukustra.medium.com/how-to-easily-bind-gameplay-ability-system-to-enhanced-input-b45ece2ca02b), Ali Elzoheiry GAS series (YouTube/Patreon, referenced via community search results)

### AttributeSet C++ Requirements
- AttributeSet classes must exist in C++ ()`UAttributeSet`-Subclass), pure blueprint definition is not possible - is in line with what we have already learned about the MCP stumbling block in SETUP.md (`InitAbilityActorInfo`/`AddSpawnedAttribute` not `BlueprintCallable`).
- Mandatory includes: `AttributeSet.h`, `AbilitySystemComponent.h`, `Net/UnrealNetwork.h`.
- Attributes as `FGameplayAttributeData`, Getter/Setter about the `ATTRIBUTE_ACCESSORS`-Macrofamily.
- **Frequently overlooked error according to forum discussion:** Older wiki/tutorial code examples `OnRep`-functions without accompanying `SetReplicated(true)` in the constructor of the attributes — leads to silent replication failure (no crash, value simply remains on client 0/outdated). **Related to our own SETUP.md stumbling block** (`Attribute`-Field vs. `AttributeName`/`AttributeOwner` for GameplayEffect modifiers via MCP: same basic pattern — GAS has several "invisible" mandatory fields that the normal blueprint editor UI automatically fills, but skips reflection-based property setting (as MCP does). **Recommendation:** For each new AttributeSet field, explicitly check whether: `GetLifetimeReplicatedProps` really lists the attribute, not just the header code.
- Create AttributeSet as a subobject in the constructor of the owner-actor`CreateDefaultSubobject<UAttributeSet>`) — the ASC then automatically finds it via `GetOrCreateAttributeSubobject`/`InitStats`No need for manual wiring in Blueprint.

### ASC initialization: Pawn-owned vs. PlayerState-owned
- For player characters, the **PlayerState-owned ASC** the approach clearly preferred by the community (also documented by GAS Companion as a standard): Owner = PlayerState, Avatar = Pawn/Character. Advantage according to research: at death/Respawn, the ASC itself does not have to be recreated/recreated, only the Avatar-Actor changes – exactly the problem that took manual work in the Respawn system in the Lyra era (see Archive.md, "Finding the Respawn Goal").
- Timing trap (corresponds with our own Lyra Fund, Archive.md "double GAS initialization"): `InitAbilityActorInfo` must be called, **after** Possession is completed - at pure `BeginPlay`-Logic is often not the case on the client yet. usual pattern: server calls init in `PossessedBy` (on the Pawn) or when setting up the PlayerState, client additionally in `OnRep_PlayerState`because replication order (Pawn vs. PlayerState) on clients is not guaranteed.
- For our planned duel/test dummies (non-player-driven), Pawn-owned ASC is still common and simpler — the community recommendation "PlayerState-owned" applies specifically to actual player-driven, respawning characters.

### Set-by-caller patterns
**Source:** [Epic Doku: Assign Set by Caller Magnitude (5.7)](https://dev.epicgames.com/documentation/en-us/unreal-engine/BlueprintAPI/Ability/GameplayEffect/AssignSetbyCallerMagnitude), [Epic Doku: Get Set by Caller Magnitude by Tag](https://dev.epicgames.com/documentation/en-us/unreal-engine/BlueprintAPI/Ability/GameplayEffect/GetSetbyCallerMagnitudebyTag), [Quod Soler: Gameplay Effect Components in UE5](https://www.quodsoler.com/blog/how-to-use-gameplay-effect-components-in-unreal-engine-5)

- Exactly confirms our SYSTEMS.md plan (a generic one) `GE_InstantDamage` with set-by-caller instead of effect per ability): modifier magnitude type set to "Set by Caller", assign your own gameplay tag as a data tag (Community Convention: prefix) `SetByCaller.`, e.g. `SetByCaller.Damage`).
- Tag-based variant ()`AssignTagSetByCallerMagnitude`/`GetSetByCallerMagnitudeByTag`) is compared to the older name-based variant (`AssignSetByCallerMagnitude`) the currently recommended, as more robust against typo/refactoring.
- **Most common runtime errors:** `FGameplayEffectSpec::GetMagnitude called for Data SetByCaller when magnitude had not yet been set by caller` - happens when the ability creates the spec, but forgets, before `ApplyGameplayEffectSpecToTarget` set the set-by-caller value. `GE_InstantDamage`/`GE_InstantHeal`/`GE_ApplyBuff`/`GE_ApplyDebuff`-Building blocks (SYSTEMS.md) means that each ability blueprint Ability must consistently build in this step, otherwise 0 damage without obvious errors in the UI (only visible in the log) - good candidate for a reusable blueprint function/Macro instead of copy paste per ability.

### Replication for List Server Prototype
- Community Consensus (Laura's Blog, Epic Forums): GAS replication "substantially works automatically" as long as (a) the ASC itself is replicated`bReplicates = true` on the Owner-Actor, ASC-`ReplicationMode` Appropriately set – sufficient for small numbers of players `Mixed`, `Full` is also okay and easier to debug for very small sessions / duels, (b) attributes really `SetReplicated(true)`/`GetLifetimeReplicatedProps` have (see above), (c) Gameplay Abilities executed on the server side (`NetExecutionPolicy` rather than being simulated locally.
- For our list server model (README, "network model") `ReplicationMode::Mixed` the default used by the community for player-controlled characters; `Minimal` is relevant for AI/NPC masses, not a priority for us at the moment.

## Solo/Small Team UE5 Multiplayer RvR/MOBA Pitfalls in General

**Sources:** [Dev Notes: Lyra Starter Game Overview](https://x157.github.io/UE5/LyraStarterGame/), [Epic Forums: Best practices to build upon Lyra](https://forums.unrealengine.com/t/best-practices-to-build-upon-lyra/515743), [GameDev.tv Community: Unreal Engine Lyra discussion](https://community.gamedev.tv/t/unreal-engine-lyra/237237), Fab-Marketplace-Recherche zu Melee-Combat-Templates (RAD_MELEE, Basic Multiplayer Melee Combat System)

- **Confirmation of our own architectural change reason from the outside:** Several sources independently confirm that Lyra is unsuitable for UE5 beginners because of the massive modularity — a cited indie developer spent "almost a month" understanding Lyra's systems in parallel with the actual UE5 learning. This coincides 1:1 with our README "architecture change" rationale — not an isolated case, but a familiar pattern.
- **Best Practice Recommendation for those who build on Lyra:** Lyra’s own namespace/base code cannot be changed if possible, but only work via the intended extension points (experiences, GameFeature plugins) – substantiates in hindsight why our attempt to enter directly into `ABP_Mannequin_Base`/Experience wiring to intervene was so fragile.
- **Network scaling:** no specific new find beyond what README already ranks correctly (standard UE5 replication designed for dozens–~100 players, large scale like Ashes of Creation needs its own interest management/server meshing investment). for our Battleground vertical slice scope (dozens of players per side), standard replication is still the right choice, no correction needed.
- **Melee Combat Animation Best Practice (from commercial multiplayer Melee templates such as RAD_MELEE, Basic Multiplayer Melee Combat System):** common, robust pattern is fighting logic (hit detection, combo counter, blocking) in its own, reusable **Actor components** Instead of packing directly into the character class — each ability/feature as its own component that can be attached to different characters. Relevant to us, it fits well with our DataTable-driven approach (SYSTEMS.md) — Hit-Detection/Combo-Timing could exist as a generic component in parallel to GAS, instead of being duplicated in individual Ability blueprints.
- **AnimMontage + AnimNotify** remains the standard building block for attack timing (hit windows via notifications instead of tick polling) — coincides with our archived knight prototype approach`AN_Melee`-Notify), no correction necessary, only confirmation that the pattern is still current.

## Recommendations for our documentary (not self-edited — for review in future session)

1. **SETUP.md:** Before further GAS expansion, explicitly verify whether: `CamelotRAW_TP` (Third Person Template, Variant "None", UE5.8) uses classic AnimBP or the new motion matching system (see Section 1) — if GAS tutorials do not fit in the future, check here first, do not immediately debug towards "GAS broken". Same trap pattern as in Lyra (animation system version ≠ tutorial assumption).
2. **SYSTEMS.md, Section 2d (Death & Respawn):** Research confirms PlayerState-owned ASC as a standard pattern for respawning player characters (section 2 above) — should be explicitly recorded as a decision in SYSTEMS.md as soon as the respawn system (third-person template base) is rebuilt, including the `OnRep_PlayerState`-Timing trap.
3. **SYSTEMS.md, set-by-caller section:** Recommendation to build early a reusable Blueprint feature/Macro for "Produce Spec + Set by Caller Tag + Apply" instead of replicating that in each ability individually — reduces the risk of breastfeeding `0-Schaden`error (section 2 above).
4. **SETUP.md, Stumbling Trap Table:** The already documented MCP Fund to the `Attribute`-Field ()`TFieldPath<FProperty>`) is not an isolated case, but is part of a recurring GAS pattern (“UI fills invisible mandatory fields automatically, reflection property sets do not”) — check against each new AttributeSet field/modifier.
5. **Myra license question (already flagged in this session):** No new external facts that mitigate the risk — if the plugin is to be used, check GAS Companion as a documented, actively maintained alternative before a decision is made.
6. **No need for correction** for: network scaling assessment (README "Scaling" already accurate), set-by-caller basic pattern (SYSTEMS.md already planned correctly), back attack/AnimNotify approach (archive.md pattern still common to the community).
